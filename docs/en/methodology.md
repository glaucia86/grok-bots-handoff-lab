# Methodology

> 🇧🇷 [Versão em português](../pt-br/methodology.md) · [Step-by-step tutorial](tutorial.md) · [README](../../README.md)

This document describes how the tests were set up and why. The results of each test are in [tests.md](tests.md).

## Common base for all tests

Every test uses the same real working conversation between me and the assistant: 40,866 characters, about 11,800 input tokens as measured by the API. From it came an answer key of 50 atomic facts, extracted by gpt-4.1 (temperature 0) and classified by weight: 9 facts of weight 3 (critical, such as decisions and approvals), 16 of weight 2 and 25 of weight 1. Five of those facts carry an approval-condition field ("only publish after X"), which is exactly the kind of detail the critique of summaries says gets lost. The note tests measure how many of these 50 facts the note preserves. The retrieval tests use 30 pointed questions generated by gpt-6.1-sol from the facts (9 of weight 3, 11 of weight 2, 10 of weight 1) and measure how many the model answers correctly with a reduced context.

Notes, answers and judges used only gpt-6-luna and gpt-6.1-sol; an older model was excluded as outdated. The answer key is the exception: it was generated by gpt-4.1, a third model, separate from the ones that answer (gpt-6-luna and gpt-6.1-sol), so that none of the evaluated models wrote its own key. The main judge is the Decisions API (gpt-6-luna), with the predicate "the answer states or clearly implies the fact" and a 0.5 threshold. A second judge, gpt-6.1-sol in JSON mode, is stricter and serves as a cross-check. It judged the notes and registries (tests 1 to 3) and conditions G, G0, T0, T, T0c and Tc (tests 6 and 7); the full chat, note only, concept search, Graphify and BM25 were judged only by the Decisions API. Input tokens come from the API `usage` field, averaged per question. Everything was done in one run per condition.

## The automatic judge, and why the Decisions API

Whether a fact survived in a note, or whether an answer is right, is not decided by a person reading case by case but by an automatic judge. The main judge was OpenAI's Decisions API running gpt-6-luna. Instead of asking the model for a free-form answer, the script passes a fixed predicate ("does the text state or clearly imply this fact?") together with the note, or the answer, and one fact from the key. The API returns a probability from 0 to 1 that the condition is true, and the fact only counts as preserved when it reaches 0.5. There were two reasons for this choice, both described in the [official documentation](https://developers.openai.com/api/docs/guides/decisions): a `predicate` question returns only a number, which removes a source of variation in a judge that runs hundreds of times; and it was built for checking conditions, which matters because each note is checked against 50 facts. The documentation itself recommends calibrating the threshold with labeled examples from your application. We used 0.5 without that calibration, which is one more reason to treat the percentages as estimates. The API is in public beta, so check the documentation before replicating.

The second judge, gpt-6.1-sol returning the list of present facts in JSON, exists because a single judge can be too generous. It is stricter and serves as a cross-check, not as the final score.

## Blocks, IDs and search

The conversation was cut into 24 blocks of about 1.7 KB, with 3 messages each, and each block got a stable ID from B01 to B24. The IDs carry no meaning; they only need to never change, because everything downstream points to them. In this repository, that is the `mark_blocks.py` script.

The search used in conditions E, G0 and G is classic BM25 (k1 = 1.5 and b = 0.75), with accent-stripping normalization and a short list of Portuguese stop words. In condition E, BM25 runs over the raw blocks and returns the top 3. In conditions G0 and G, it runs over the registry items and returns the top 5. In condition G, the blocks cited by those 5 items are ranked by the sum of the scores of the items citing them, and the top 3 enter the context. Whenever raw blocks enter, the text is split within a cap of about 1,500 tokens (estimated at 3.6 characters per token), and when a block does not fit, the paragraphs with the most query terms are kept. In this repository, that lives in `common.py` and `answer.py`.

The concept search of test 4 (condition C) used the page structure generated by Graphify without a model, plus our own keyword-concept script. It is not included in this version of the repository because it depends on the structure generated by Graphify; its numbers appear in the tables as a reference.

## Answers and tokens

Answers were generated with a fixed system instruction: answer only from the provided context, say it is not there when the context does not contain the information, and use at most 120 words. That cap is why the 5 broad questions of test 4 are not comparable with each other. Reported input tokens come from the API `usage` field, averaged per question, not character-based estimates. The exception is the columns marked "Est. tokens" in test 3, which are estimates from text length.

## What the methodology does not control

Everything was done in one run per condition, on a single conversation of about 11.8k tokens. The answer key, the questions and the judges are all model-generated, and none went through human review. The questions came from the same facts that generated the registry, which favors keyword search. Differences of 1 to 4 correct answers may be noise. The source-ID check is approximate, by keyword overlap, and the registries were not checked for hallucination. So read the numbers as preliminary evidence, not proof.

## Data not in this repository

The original conversation, the answer key, the generated questions, the notes, the registries, the ledgers, the logs and the raw result files were left out because they contain private conversation data. The tables in [tests.md](tests.md) are the aggregated results. To run the method, use your own conversation or the synthetic conversation in [examples/](../../examples).
